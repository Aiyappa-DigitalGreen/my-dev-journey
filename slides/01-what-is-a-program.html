What is a program?

By the end of this deck you will know the three properties every program must have — and why every bug you will ever write is one of them.

1️⃣ The problem it solves

A helper with no common sense

  • Unbelievably fast — thousands of operations a second.
  • Never bored, never tired — task #1000 gets the same care as task #1.
  • Completely without common sense — it cannot guess. Ever.

A program is how you get useful work out of a helper that understands nothing.

2️⃣ The picture

A recipe for someone who has never seen food

A human recipe says "boil the water." A human fills the gaps.

A computer recipe must say: pick up the vessel · walk to the tap · turn the tap · wait for 200ml · turn it off.

Every gap you leave, it falls into.

🤖 Executed literally

The tea that never was

take water          → held in bare hands. No vessel exists.
boil it             → stove was never turned on.
add tea powder      → added it TO THE FLOOR.
boil 5 MORE minutes → "more" than what? Nothing boiled.
pour it to cup      → no cup exists. No straining → leaves in drink.
add sugar           → how much? ...adds sugar forever. ♾️

Output: a floor, some leaves, and infinite sugar.

⭐ The core

Three properties. That's the whole concept.

  • EXACT — the instruction is there but too vague to act on. "Take water" — how much, into what?
  • COMPLETE — the instruction is missing entirely. Turn on the stove. Strain the leaves.
  • ORDERED — every step present and precise, wrong sequence. Cup filled before water exists.

Every bug you will ever write is one of these three — a 2am production crash is one of them in a costume.

The uncomfortable part

You cannot see your own gaps

Nobody writes "turn on the stove" — not from carelessness, but because your brain already knows how tea works and patches the hole silently.

The step you never questioned is the step you never wrote.

That is the entire argument for code review and tests: a second brain that doesn't share your assumptions.

🧭 Where & when

A real login screen

check email isn't empty      ← exact: which box? what is "empty"?
check password isn't empty
send both to the server
WAIT for the answer          ← complete: drop this and home opens
                                too early, before the server replies
if correct → home screen     ← ordered: check before you send
if wrong   → red error
🧭 When NOT to — the senior signal

Knowing when not to write it

  • When you'll do it twice. Automating a rare task is a net loss — the program still has to be maintained.
  • When it needs judgement, not rules. If you can't say the rules out loud, you can't write them down.
  • When a tool already exists. The fastest program is the one someone else wrote.
  • From scratch, step 1 is not code — it's writing the steps in plain English.
🎤 Q&A recall

Test your understanding

  • Q: What is a program?
  • A: An ordered sequence of unambiguous instructions a machine executes literally — it supplies no intent of its own, so anything left implicit becomes a defect.
  • Q: Why do experienced developers still write bugs?
  • A: The gaps are invisible to the author — domain knowledge patches them silently, exactly like never writing "turn on the stove."
Recap

What we locked in

  • A program = instructions followed literally, in order, with no guessing.
  • Exact · Complete · Ordered — every bug is one of these three.
  • Your brain hides your own gaps. That's why review and tests exist.
