Backend · Auth · Topic 09

The server's notebook, the browser's pocket.

Sessions and cookies: how a forgetful server remembers who you are.

1 · The problem

The server forgets you instantly

POST /login  (username + password) → "Login OK ✅"
GET  /feed                         → "Who are you?" 🤨
  • HTTP is stateless: every request looks like a stranger.
  • Sending the password every time is slow and risky.
2 · The picture

The forgetful bank clerk 🏦

  • Clerk's notebook = session store (server)
  • One row = a session
  • Card handed to you = session ID
  • Wallet that shows the card automatically = cookie
3 · Session

The record lives on the server

8f3k29xq7b → user: Aiyappa, logged in 10:30
  • The browser gets only the random ID.
  • A name on the card could be forged. A random ID can't be guessed.
4 · Cookie

Stored and sent automatically

Server  → Set-Cookie: sessionId=8f3k29xq7b
Browser → Cookie: sessionId=8f3k29xq7b   (every request)
  • A cookie is storage + delivery, not a login method by itself.
  • No code needed to send it. The browser does it.
5 · Where & when

When to reach for sessions

  • Use: browser websites, need instant logout or ban.
  • Not: mobile apps and APIs → tokens in a header.
  • Logout: delete the row, and the card is useless.
Interview

Quick answers

  • Q: Session vs cookie? A: Server-side record vs browser-stored value; the ID rides in the cookie.
  • Q: Why a random ID? A: It can't be guessed or forged.
  • Q: Sessions or tokens? A: Sessions for browsers + instant revocation; tokens for mobile/APIs.
Recap

What we locked in

  • Session = notebook on the server. Cookie = pocket in the browser.
  • Random ID, never the user's details.
  • Next: tokens, JWT, expiry and refresh.
