Track A · W1 · Topic 03

Jars with labels.

val · var · $ — how a program remembers things, and why the sealed jar is the one you should reach for.

1️⃣ The problem

Hardcoded facts, and no memory

  • Nothing has a single home. A name in 20 of 200 lines = 20 edits and one miss. Twenty copies of a fact are twenty chances to be wrong.
  • The program can't remember. Real programs discover things while running — what the user typed, what the server said. With no jars, it evaporates before the next line.
2️⃣ The picture

Jars with paper labels

You don't carry two kilos of rice around the kitchen. You pour it into a jar, write rice on the label, and from then on you say "pass me the rice."

jar = variable · label = name · contents = value

⚠️ The token everyone gets wrong

= is not "equals"

val name = "Aiyappa"

In school = states a fact, true in both directions.

In code it is an arrow pointing left: take the thing on the RIGHT and put it INTO the jar on the LEFT.

An action, not a fact. Its real name is assignment.

👀 The quotes rule, doing new work

One character changes everything

println("name")   // → name       the four letters
println(name)     // → Aiyappa    the contents of the jar

Quotes ON = don't interpret, it's plain text.
Quotes OFF = interpret it as a label, go fetch what's inside.

The two jars

Sealed vs refillable

val score = 0
score = 10        // ❌ error: 'val' cannot be reassigned.

var score = 0
score = 10        // ✅  no `var` on line 2 — var CREATES the jar, once
⭐ The senior idea

Why does val exist at all?

var can do everything val can, plus more. So why ever seal a jar?

Because most bugs are something changing when you didn't expect it to.

A phone number in a var, in a 3,000-line app. One line you've never read quietly changes it. Now the SMS goes to the wrong person.

⭐ The rule

Default to val

  • A val makes that entire class of bug impossible — not unlikely. The compiler proves it before the program runs.
  • A val is a promise the compiler enforces: this will not change from under you.
  • Reach for var only when you can name the reason it must change. "Might need it later" is a guess — converting costs one keystroke.
  • 🔥 Android: shared mutable state is the #1 source of mobile bugs. Compose is built around controlling who may change what.
🎓 One layer deeper

Should this be stored at all?

seatsLeft as a val? Correct here. In a real app, a var?
Better: don't store it — compute totalSeats - registered, so it can never disagree with reality.

Two facts that must match are two facts that will eventually disagree.

2️⃣ Templates — the picture

A pre-printed certificate

This certifies that __________ completed __________ on __________.

The sentence is printed once and stays readable. The blanks get filled per student.

$ marks a blank.

💻 String templates

Punching a hole in the quotes rule

println("Workshop: $name")      // → Workshop: Aiyappa

println("$cityworkshop")        // ❌ hunts for jar "cityworkshop"
println("${city}workshop")      // ✅ Madikeriworkshop

println("Next year: ${count + 1}")   // more than a bare fetch
println("Price: \$500")              // a literal dollar sign
🧭 When NOT to — senior signals

Two places templates are dangerous

  • 🔒 Never build a database query with them. A user types something that isn't a name, and the database runs it — SQL injection, still one of the most common serious breaches worldwide. Use parameterised queries.
  • 📱 Never for user-facing Android text. UI text belongs in string resources with placeholders, so the app can be translated. A template hardcodes English forever.
  • Don't stuff calculations inside ${ } — compute into a val first.
🐛 Real bug, day one

The stale build

04_templates.kt printed 03_workshop.kt's output — no error at all.

.build kept EVERY class ever compiled, and the script did:
   find . -name "*Kt.class" | head -1     ← "grab the first one"

Which property failed? COMPLETE — a missing step, exactly like never writing "turn on the stove."
This is why Android Studio has Build → Clean Project.

Recap

What we locked in

  • = is an arrow pointing left, not "equals".
  • Quotes on = plain text. Quotes off = fetch the jar.
  • Default to val. A sealed jar is a bug that can't happen.
  • $ = a blank in a pre-printed sentence. Never in a query, never in UI text.
  • Next: types — what kind of thing is in the jar.
